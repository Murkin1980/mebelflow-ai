# MebelFlow Conversational Interface

Специализированный UI/UX-навык для MebelFlow AI.

Основан на принципах системного frontend design review: frictionless insight-to-action, quality craft и trustworthy building. Адаптирован под разговорную приёмку мебельных заказов.

## 1. Главная задача интерфейса

Пользователь не должен «проектировать кухню».

Он должен:

1. сказать или написать пожелание;
2. увидеть немедленное изменение схемы;
3. понять, что произошло;
4. легко исправить;
5. перейти к следующему логичному решению;
6. получить ориентировочную цену;
7. отправить заявку.

Схема служит визуальной обратной связью для разговора.

## 2. Режимы навыка

### CREATE

Создать новый экран, компонент или flow.

Перед кодом зафиксировать:

- пользовательскую задачу;
- текущий этап;
- одно основное действие;
- ожидаемый результат действия;
- состояния loading/success/error/empty;
- поведение на узком Android-экране;
- доступность голосового и текстового пути.

### REVIEW

Проверить существующий интерфейс и выдать замечания:

- BLOCKING;
- MAJOR;
- MINOR.

Каждое замечание должно содержать:

- место;
- проблема;
- влияние на пользователя;
- точное исправление;
- критерий проверки.

## 3. Три обязательных столпа

### 3.1 Frictionless: от мысли к видимому результату

- На каждом экране одно основное действие.
- Следующий шаг очевиден без инструкции.
- Голос и текст доступны рядом, но не конкурируют.
- После команды схема обновляется сразу.
- Не заставлять клиента выбирать модуль из технического каталога, если он может сказать фразу.
- Не показывать более 3 рекомендаций одновременно.
- В любой момент доступны «Назад» и «Отменить изменение».
- Не прятать критический конфликт размеров.
- Не требовать регистрацию до появления первой полезной схемы.

Целевой показатель: типовое изменение выполняется одной фразой или максимум тремя касаниями.

### 3.2 Quality Craft: точность и мебельный характер

Визуальная концепция:

> «Спокойная мастерская»: тёплая, профессиональная, тактильная, без ощущения банковского dashboard или игрового приложения.

Использовать:

- много свободного пространства вокруг схемы;
- чёткую размерную типографику;
- спокойные нейтральные поверхности;
- один фирменный акцент tenant;
- текстуры дерева только в этапе стиля;
- аккуратные инженерные линии;
- ясную иерархию;
- 4/8px spacing system;
- design tokens;
- адаптивную типографику;
- плавные, функциональные переходы 150–250 мс.

Не использовать:

- бесконечные карточки;
- фиолетовые AI-градиенты;
- glassmorphism ради эффекта;
- dashboard sidebar в клиентском widget;
- мультяшные награды;
- декоративный 3D;
- перегруженные панели;
- скрытые drag-жесты как единственный способ управления;
- мелкие подписи размеров;
- чисто цветовые сигналы без текста/иконки.

### 3.3 Trustworthy: пользователь понимает статус AI

Всегда различать:

- что сказал клиент;
- что поняла система;
- что применено;
- что требует уточнения;
- что является предварительным;
- что подтверждает мебельщик позднее.

Обязательно:

- показать распознанный текст голосовой команды;
- при средней уверенности запросить подтверждение;
- объяснить конфликт простыми словами;
- дать варианты исправления;
- обозначить ориентировочную цену как диапазон;
- показать disclaimer до заказа/PDF;
- не писать «проект готов к производству»;
- не скрывать ошибку AI;
- не терять введённые данные при ошибке сети.

## 4. Информационная архитектура widget

Постоянные зоны:

1. **Progress Header** — этап и короткий прогресс.
2. **Conversation Area** — вопрос, ответ и уточнение.
3. **Scheme Stage** — SVG, размер стены, выбранный модуль.
4. **Context Action Bar** — одно основное действие, undo и помощь.
5. **Status Line** — сохранено, слушаю, применяю, требуется уточнение.

На мобильном:

- схема занимает 35–50% viewport на этапах компоновки;
- диалог и действие остаются видимыми;
- клавиатура не закрывает основной CTA;
- touch target не меньше 44×44 CSS px;
- safe areas учитываются;
- bottom sheet не перекрывает выбранный модуль.

## 5. Разговорный цикл

```text
INPUT → TRANSCRIPT → INTERPRETATION → VALIDATION → APPLY → EXPLAIN → NEXT
```

### INPUT

- кнопка микрофона;
- текстовое поле;
- примеры допустимых фраз контекстны текущему этапу.

### TRANSCRIPT

Показать, что распознано:

> «После мойки поставь посудомойку 600»

Доступно быстрое исправление текста.

### INTERPRETATION

При необходимости показать короткую интерпретацию:

> Добавить ПММ 600 мм после мойки

### VALIDATION

Если команда конфликтует:

> На стене не хватает 180 мм. Можно уменьшить тумбу с ящиками до 400 мм или заменить мойку 800 на 600 мм.

### APPLY

Изменение анимируется только для ориентации пользователя.

### EXPLAIN

> Посудомойка 600 мм добавлена после мойки. Осталось 1000 мм.

### NEXT

> Что поставить в оставшееся пространство?

## 6. Прогрессивное раскрытие

Показывать только нужное текущему этапу.

Не показывать стили до завершения компоновки.

Этапы:

1. Размеры.
2. Коммуникации.
3. Нижний ряд.
4. Верхний ряд.
5. Стиль.
6. Цена.
7. Контакт и результат.

## 7. SVG-схема

Обязательные свойства:

- пропорциональное отображение;
- общая размерная линия;
- ширина каждого блока;
- выбранный блок;
- понятные пиктограммы техники;
- свободный остаток;
- предупреждение на конкретном месте;
- front view как основной;
- нейтральный monochrome до этапа стиля;
- цвет включается после выбора стиля.

Выбранный блок должен быть понятен не только цветом:

- контур;
- маркер;
- подпись;
- aria description.

## 8. Голос

Состояния микрофона:

- idle;
- requesting_permission;
- listening;
- processing;
- transcript_ready;
- applying;
- error.

Нельзя:

- начинать запись без явного действия;
- скрывать факт записи;
- отправлять запись повторно без согласия;
- оставлять пользователя без текстовой альтернативы.

## 9. Ошибки

Формула сообщения:

```text
Что произошло → почему это важно → что можно сделать
```

Плохо:

> Invalid layout.

Хорошо:

> Модули занимают 3180 мм, а длина стены — 3000 мм. Уменьшите один из шкафов или выберите предложенный вариант.

Ошибка должна сохранять состояние и предлагать действие.

## 10. Calm Gamification

Разрешено:

- прогресс;
- чек выполненного этапа;
- «Все размеры помещаются»;
- «Техника учтена»;
- «Компоновка готова»;
- финальная карточка результата.

Запрещено:

- конфетти после каждого шага;
- очки;
- монеты;
- streak;
- искусственная срочность;
- манипулятивные countdown;
- ложная экономия.

## 11. Design tokens

Обязательные группы:

- color.surface;
- color.text;
- color.brand;
- color.success;
- color.warning;
- color.danger;
- color.selection;
- spacing;
- radius;
- shadow;
- typography;
- motion;
- dimensionLine.

Не использовать случайные hardcoded значения внутри компонентов.

## 12. Accessibility

Минимум WCAG 2.2 AA для основного flow.

Проверить:

- keyboard;
- screen reader labels;
- focus order;
- focus visible;
- contrast;
- zoom 200%;
- reduced motion;
- touch targets;
- error association;
- voice alternative;
- SVG title/description;
- status announcements через aria-live.

## 13. Производительность

- не подключать 3D/WebGPU;
- SVG не должен перерисовывать весь widget без причины;
- оптимизировать шрифты;
- не блокировать first interaction AI SDK;
- skeleton только там, где он отражает реальное ожидание;
- optimistic UI допускается только с откатом;
- Android mid-range является базовым устройством.

## 14. Обязательные состояния каждого компонента

- default;
- hover, где применимо;
- active;
- focus-visible;
- disabled;
- loading;
- success;
- warning;
- error;
- empty;
- offline, если зависит от сети.

## 15. Review gates

UI-срез нельзя считать завершённым без:

- mobile screenshot 360×800;
- desktop screenshot;
- keyboard pass;
- screen reader smoke;
- reduced motion pass;
- slow network pass;
- empty/error states;
- visual regression;
- проверенного CTA;
- подтверждённого disclaimer;
- проверки отсутствия generic AI aesthetics.

## 16. Формат отчёта ревью

```markdown
# UI Review

## User task

## Direction

## Blocking

## Major

## Minor

## Accessibility

## Mobile

## Trust and AI transparency

## Verification evidence

## Decision
PASS / PASS WITH FIXES / FAIL
```

## 17. Источники принципов

Локальный навык адаптирован под MebelFlow AI на основе:

- Microsoft `frontend-design-review`;
- подхода Frictionless / Quality Craft / Trustworthy;
- anti-generic frontend guidance;
- требований FOUNDATION.md и TECH_SPEC.md.

Не копировать внешние визуальные бренды и готовые экраны. Использовать принципы, а не чужую айдентику.
